# Security

## Reporting something

Open a [private security advisory](https://github.com/a-khavish/Quenchkey/security/advisories/new)
rather than a public issue, and give it as long as you think reasonable before
publishing. There is no bounty; there is a name in the release notes if you
want one.

Please include what an attacker has to have, what they get, and how you
verified it. A working reproduction against a vault you made yourself is worth
more than a description.

## What this protects against

- **Someone who obtains a `.qkey` file.** Its key is in the vault, which they
  do not have. Once the key is destroyed the file is unreadable to everybody,
  including the vault holder.
- **Someone who obtains the vault file.** They face Argon2id at about a second
  per guess on ordinary hardware. I measured 256 MiB, one pass,
  parallelism 4, which is roughly 760 guesses/sec on a 48 GB machine
  parallelised. A passphrase generated by this tool (157 bits) is not
  reachable. A passphrase you invented may well be.
- **Modification of anything.** Every format here is authenticated: the vault
  header is associated data for its payload, each blob chunk covers the header
  and the key block, an identity card signs its own key, and the audit record
  covers its own header. An edited file fails rather than returning wrong data.
- **A clock set backwards.** The vault keeps a watermark and never accepts an
  earlier time, and reports when it sees one. A timestamp from an authority
  corrects it further.
- **A rewritten event log.** The chain makes the log self-consistent or not;
  the anchor, published somewhere the vault is not, is what makes a rewrite
  detectable rather than merely possible to notice.

## What it does not protect against

Stated here, in the README, and in the application under *What this does not
protect against* — the same list in all three places.

- **A file you have already opened.** The extracted copy is an ordinary file.
  Expiry destroys the key to the locked copy and reaches nothing else. There
  is no recall.
- **A copy of the vault folder, taken before a deadline and restored after.**
  Local expiry is tamper-**evident**, not tamper-proof. This is the honest
  limit of anything that runs only on a machine somebody else controls.
- **A shared file's deadline**, because it has none and cannot have one: the
  key travels inside the file, so there is nothing anywhere left to destroy.
  The header says so, readably, without a passphrase. Use a handover if the
  deadline matters and the recipient runs Quenchkey.
- **A recipient's own machine.** A handover puts the deadline in their vault,
  where their sweep enforces it. They can restore a backup of their vault
  after the deadline, exactly as you can with yours.
- **Anything while the vault is unlocked.** Keys are in memory. Another
  process running as you can read that memory, and the operating system may
  page it to disk. Lock the vault when you are not using it; auto-lock is on
  by default.
- **A compromised machine.** A keylogger takes the passphrase. Malware running
  as you can read anything you can read. Nothing in userspace fixes that.
- **Forgetting the passphrase.** There is no reset and no back door. Recovery
  shares are the only protection and must be set up in advance.

## Things deliberately not built

Each of these appears in comparable software and none of it works:

- Screenshot or screen-recording blocking. Not possible from a user account,
  and a camera defeats every version of it anyway.
- "Only our application can open these files." A documented format and a
  standalone decryptor are shipped precisely to contradict this.
- Folders hidden or made inaccessible by permissions, presented as
  protection. Anybody with your account undoes it.
- Remote deletion on somebody else's machine. There is no mechanism. They own
  the machine.
- Interception of application launches to demand a passphrase. Every version
  of the trick is defeated by running the binary directly.

## Cryptography

| | |
|---|---|
| Key derivation | Argon2id, calibrated at first run, parameters stored in the header |
| Vault and blobs | ChaCha20-Poly1305 (default) or AES-256-GCM |
| Streaming | 1 MiB chunks; nonce = 4-byte random prefix + 8-byte big-endian counter; header and key block as associated data on every chunk |
| Signatures | Ed25519, for certificates of destruction, identity cards and audit records |
| Key agreement | X25519, derived from the signing seed by HKDF-SHA256 under a separate info string |
| Recovery shares | SLIP-39 |
| Timestamps | RFC 3161; request built in-tree, verification handed to openssl |
| Digests | SHA-256 throughout, with a domain separator per use |

Everything comes from [`cryptography`](https://cryptography.io) and
[`argon2-cffi`](https://argon2-cffi.readthedocs.io). No primitive is
implemented here.

## Verifying a release

Every claim above has a test. `python -m pytest` runs them; `tests/` is
readable and the test names are sentences. The ones that matter most are the
negative claims — that no file key is in an audit record, that a handover
cannot be opened by its sender, that a copy made by hand survives a loan —
because those are the claims that rot quietly if nobody checks them.
